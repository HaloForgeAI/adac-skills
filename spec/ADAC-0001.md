# ADAC-0001: Acceptance-Driven Agentic Coding

Status: Draft  
Version: 0.1.0  
Owner: HaloForgeAI  
Created: 2026-05-30  
Scope: AI-assisted software engineering tasks that may affect production behavior, shared modules, user experience, performance, data, security, release flow, or long-term maintainability.

## Abstract

Acceptance-Driven Agentic Coding (ADAC) is a formal engineering mechanism for using coding agents safely and productively. ADAC requires a task to define context, boundaries, acceptance evidence, and human gates before implementation is allowed to expand.

ADAC does not treat tests, coverage, or model confidence as final proof. It treats them as evidence inside a broader delivery record. The mechanism is designed for complex systems where correctness depends on business behavior, historical regressions, resource lifecycle, concurrency, observability, and rollout decisions.

## Normative Language

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as requirement levels in the style of RFC 2119.

## 1. Problem Statement

Coding agents can rapidly produce plausible plans, patches, tests, and documentation. In complex engineering work, plausibility is not enough. Agentic work can also amplify wrong context, vague goals, unsafe abstractions, brittle tests, and review overload.

ADAC addresses this by moving the control point earlier:

- define what "done" means before implementation;
- bind the agent to system context and explicit non-goals;
- require acceptance checks that map to real risks;
- preserve human decision points where correctness cannot be delegated.

## 2. Core Model

Every ADAC task is governed by four controls.

### 2.1 Context

Context is the minimum reliable knowledge needed to avoid guessing.

An ADAC task **MUST** identify the source materials the agent is expected to use: code paths, architecture notes, business flows, prior incidents, logs, metrics, test directories, environment constraints, and release history.

An ADAC task **SHOULD** state known unknowns. If a critical unknown cannot be resolved locally, the task **MUST** create a human gate instead of letting the agent invent an answer.

### 2.2 Spec

Spec is the boundary contract for the task.

An ADAC task **MUST** define:

- target behavior;
- non-goals;
- changed and unchanged interfaces;
- ownership boundaries;
- compatibility expectations;
- rollback or fallback behavior when applicable.

For production or shared-module work, the task **MUST NOT** rely on "make it better" as a sufficient requirement.

### 2.3 Evals

Evals are acceptance checks derived from real risks.

An ADAC task **MUST** include at least one acceptance item for each relevant risk category:

- user-visible behavior;
- historical regression;
- integration or lifecycle correctness;
- performance or resource usage;
- observability and diagnosis;
- rollout, fallback, or migration safety.

ADAC **SHOULD** prefer behavior and regression checks over internal implementation coverage. Coverage MAY be recorded as supporting evidence, but coverage MUST NOT be the primary acceptance claim unless coverage itself is the product requirement.

### 2.4 Gates

Gates are human decision points.

An ADAC task **MUST** define gates for decisions that require domain judgment, including architecture boundaries, concurrency risks, data loss risks, security/privacy concerns, release switches, irreversible migrations, and acceptance interpretation.

Agents MAY prepare evidence for a gate. Agents MUST NOT silently pass a gate by assuming approval.

## 3. Risk Classes

ADAC uses four risk classes to scale ceremony.

| Class | Name | Typical work | Required ADAC depth |
|---|---|---|---|
| A | Local | small isolated code or document change | short acceptance checklist |
| B | Shared | shared utility, user-facing feature, non-critical integration | full plan, focused evidence |
| C | Critical path | concurrency, resource lifecycle, performance, release path, data migration | full plan, independent verification, explicit gates |
| D | High-impact | security, payment, legal, irreversible data, broad rollout | full plan, separate owner approval, rollback drill |

If risk is unclear, classify upward until evidence supports lowering it.

## 4. Lifecycle

### 4.1 Intake

The owner or agent **MUST** state the task, business/user goal, target repository or module, risk class, and expected deliverable.

### 4.2 Context Pack

The agent **MUST** gather and list the context used for the task. The context pack SHOULD include direct code paths, docs, operational data, prior incidents, and test entry points.

The context pack MUST distinguish verified facts from assumptions.

### 4.3 Acceptance Spec

Before implementation, the task **MUST** produce an acceptance matrix with:

- acceptance ID;
- risk category;
- expected behavior or invariant;
- verification method;
- evidence artifact;
- owner/gate when human judgment is required.

### 4.4 Agent Work Plan

The agent work plan **MUST** decompose implementation into small, reviewable steps. For class C or D work, the plan SHOULD separate exploration, implementation, verification, and release preparation.

When subagents are used, each subagent SHOULD receive only the context needed for its role and SHOULD produce raw evidence rather than final approval.

### 4.5 Implementation Loop

Each implementation step **MUST** map back to at least one acceptance item. If a patch introduces new risk, the acceptance matrix MUST be updated before continuing.

The agent SHOULD avoid broad refactors unless the refactor is itself an accepted deliverable with explicit evidence.

### 4.6 Evidence Package

Before declaring completion, the task **MUST** record evidence:

- commands or checks run;
- test, profile, telemetry, log, screenshot, trace, or manual verification artifacts;
- known failures or skipped checks;
- residual risk;
- rollback/fallback readiness when applicable.

### 4.7 Human Gates

The owner **MUST** review required gates before the work is treated as accepted. Gate decisions MUST record one of:

- `approved`;
- `approved-with-risk`;
- `blocked`;
- `not-applicable`.

### 4.8 Assetization

When a task produces reusable context, checks, scripts, or operational knowledge, the team SHOULD add them to a durable asset: skill, spec, runbook, checklist, test harness, telemetry dashboard, or incident note.

## 5. Required Artifacts

For class B and above, an ADAC task **MUST** produce:

- ADAC plan;
- context pack;
- acceptance matrix;
- implementation/evidence log;
- gate record for any required human decision.

For class C and D, the task **MUST** also produce:

- rollback or fallback path;
- independent verification record;
- residual risk statement.

## 6. Acceptance Matrix Requirements

An acceptance item is valid only if it is checkable. Each item MUST include:

- **ID**: stable identifier, for example `AC-01`;
- **risk**: behavior, regression, performance, observability, rollout, security, or other named category;
- **criterion**: expected externally meaningful behavior or invariant;
- **method**: command, scenario, manual inspection, profile, telemetry, log review, or gate review;
- **evidence**: artifact or result to record;
- **owner**: agent, human reviewer, QA, release owner, or named team role.

Vague items such as "code looks good", "improve quality", or "make performance better" are not valid acceptance items unless converted into checkable criteria.

## 7. Human Gate Requirements

Human gates are mandatory when work touches:

- public or shared API contracts;
- concurrency, locking, scheduling, async boundaries, or lifecycle ownership;
- persistent data or migrations;
- authentication, authorization, privacy, or secrets;
- release toggles, rollback, canary, or operational response;
- user-visible behavior where business judgment is needed;
- any area where the agent cannot verify correctness from available context.

## 8. Anti-Patterns

ADAC-compliant work MUST NOT:

- start broad implementation before defining acceptance;
- treat passing tests as proof that no bug exists;
- replace behavior/regression checks with coverage percentage;
- let an agent rewrite scope to avoid hard acceptance items;
- hide skipped checks;
- remove fallback paths without explicit approval;
- merge high-risk agent output without a human gate.

ADAC-compliant work SHOULD NOT:

- create abstractions for hypothetical future reuse;
- expand scope because the agent found adjacent improvements;
- use generated documentation as evidence unless it is tied to a checkable artifact.

## 9. Completion Definition

An ADAC task is complete only when:

1. required artifacts exist;
2. acceptance items have evidence or explicit skipped-risk notes;
3. gates have recorded decisions;
4. residual risk is stated;
5. reusable learnings are either assetized or explicitly declined.

## 10. Versioning

ADAC specifications use semantic versioning for the mechanism and numbered ADAC documents for major policy changes. Backward-incompatible process changes require a new ADAC document or a major version increment.
